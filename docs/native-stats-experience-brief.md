## What this is and why

The web repo just shipped (commit `8a4a265`) two new public, unauthenticated,
read-only JSON routes so the home-stats strip and work-experience timeline —
previously rendered only server-side — can be fetched over the network:

- `GET /api/stats` → `{ data: { value: string; label: string }[] }`
- `GET /api/experience` → `{ data: ExperienceItem[] }`

```ts
interface ExperienceItem {
  company: string;
  role: string;
  period: string;
  location: string;
  description: string;
  tags: string[];
  current?: boolean;
}
```

Both routes: `Cache-Control: public, max-age=0, s-maxage=3600,
stale-while-revalidate=86400`, no `Access-Control-*` headers, no auth/session/
Origin guard — same public class as the `GET /api/markdown` route this app
already calls. `EXPO_PUBLIC_API_ORIGIN` + this app's existing `apiRequest`
helper (`src/lib/api/client.ts`) work against them unchanged; the `origin`,
`x-mg-client`, and `x-mg-session` headers it always attaches are harmless
here — these routes ignore them.

**Important context — this app already has two unrelated mechanisms for this
same data, and this task adds a third:**

1. **`scripts/sync-content.ts`** (`bun run sync-content`) copies typed data
   files from the web repo's filesystem (`~/projects/my-portfolio/lib/data/`)
   into `src/data/` + `src/types/` at **dev/build time**. `DATA_MODULES`
   already includes `"experience.ts"` — it's synced today, split into
   `src/types/experience.ts` (the interface) and `src/data/experience.ts`
   (the array) by `splitExperience()`. It does **not** include a `stats.ts`
   entry, because until this web-repo change, stats lived inline in a
   component, not as a `lib/data/` file — there was nothing to sync.
2. **`src/features/home/constants.ts`** hand-duplicates the stats array as
   `STATS` (`as const`), consumed by `src/features/home/components/stats-strip.tsx`.
   This is not generated by the sync script and can drift from the web repo's
   source silently.
3. **This task**: a genuine runtime network fetch of both endpoints, via
   this app's existing `apiRequest` + TanStack Query pattern (see
   `src/lib/api/markdown.ts` / `src/features/blog/use-article-markdown.ts`),
   so the data can update **without an app rebuild**.

The recommended design keeps all three working together rather than ripping
two out: the bundled/synced copy remains the **instant-paint, offline-safe
default** (via TanStack Query `initialData`), and the live fetch **quietly
revalidates** in the background exactly like `useArticleMarkdown` already
does for blog bodies. This preserves the app's offline-first architecture
(`src/lib/query-client.ts`'s `AsyncStorage` persistence + `NetInfo` online
manager) instead of making stats/experience a hard network dependency.

## Task 2 — fetch clients

Mirror `src/lib/api/markdown.ts` exactly (same `apiRequest` import, same
error-on-non-2xx shape):

`src/lib/api/stats.ts`:
```ts
import { apiRequest } from "./client";
import type { StatItem } from "@/data/stats";

export async function fetchStats(): Promise<StatItem[]> {
  const response = await apiRequest("/api/stats");
  if (!response.ok) {
    throw new Error(String(response.status));
  }
  const body = (await response.json()) as { data: StatItem[] };
  return body.data;
}
```

`src/lib/api/experience.ts`:
```ts
import { apiRequest } from "./client";
import type { ExperienceItem } from "@/types/experience";

export async function fetchExperience(): Promise<ExperienceItem[]> {
  const response = await apiRequest("/api/experience");
  if (!response.ok) {
    throw new Error(String(response.status));
  }
  const body = (await response.json()) as { data: ExperienceItem[] };
  return body.data;
}
```

(`StatItem` comes from `src/data/stats.ts` if Task 1 ran first; if you skip
Task 1, define `StatItem` inline in `src/lib/api/stats.ts` instead — do not
block Task 2/3/4 on Task 1.)

## Task 3 — hooks with offline-safe `initialData`

Mirror `src/features/blog/use-article-markdown.ts`'s `useQuery` shape.
Seed `initialData` from the bundled copy so the screen paints instantly and
works offline; the query then revalidates against the live endpoint per
`src/lib/query-client.ts`'s default `staleTime` (5 min).

`src/features/home/use-stats.ts`:
```ts
import { useQuery } from "@tanstack/react-query";
import { fetchStats } from "@/lib/api/stats";
import { stats } from "@/data/stats"; // or `STATS` from "./constants" if Task 1 was skipped

export function useStats() {
  return useQuery({
    queryKey: ["stats"],
    queryFn: fetchStats,
    initialData: stats,
  });
}
```

`src/features/experience/use-experience.ts`:
```ts
import { useQuery } from "@tanstack/react-query";
import { fetchExperience } from "@/lib/api/experience";
import { experience } from "@/data/experience";

export function useExperience() {
  return useQuery({
    queryKey: ["experience"],
    queryFn: fetchExperience,
    initialData: experience,
  });
}
```

## Task 7 — optional: offline persistence (a decision, not a mandate)

`src/lib/query-client.ts`'s `shouldDehydrateQuery` currently only persists
`queryKey[0] === "markdown"` to `AsyncStorage`. `initialData` (Task 3)
already guarantees an instant, fully offline render every launch, so this is
**not required** for correctness. Only extend the allowlist to also persist
`"stats"` / `"experience"` query keys if you specifically want the
*network-refreshed* value to survive an app restart while offline (as
opposed to falling back to the Task-1 bundled copy each cold start). If you
do this, update the doc comment above `shouldDehydrateQuery` accordingly.
